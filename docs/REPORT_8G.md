# SuperMimic 复现报告：8GB 笔记本单卡跑通人形全身动作跟踪

> 复现对象：**SuperMimic: Scaling Humanoid Whole-Body Control with One Differentiable World Model**
> （Qiayuan Liao, Yiyang Shao, Junfeng Long, Kevin Zakka, Roberto Horowitz, Pieter Abbeel, Koushil Sreenath — UC Berkeley，CoRL 2026，arXiv:2610.28480）
>
> 硬件：**RTX 4060 Laptop，8 GB 显存**，Windows 11，驱动 581.80
> 结果：LAFAN1 40 条动作，**归一化回报 0.854（宏平均）/ 0.859（帧长加权），7/40 失败**
> 对照：论文 LAFAN1 0.82（1×H100，1.2 h）；上游复现 0.904（1×RTX 5090，+锚点观测）

---

## 0 一句话结论

在一台 8 GB 显存的消费级笔记本上，用 512 并行环境（论文的 1/8）、想象时域 16（论文的 1/2）、纯 eager 模式（论文为 `torch.compile`），53 小时累计训练 12.65 万迭代，达到 **0.854** 的 40 条宏平均回报——**比论文 LAFAN1 报的 0.82 高，比上游复现在 5090 上跑出的 0.904 低 5.5%**。差距主要来自每条迭代的样本量只有上游的 1/8，而不是方法本身跑不通。

---

## 1 复现目标与约束

论文的核心主张是：用一个可微世界模型 + 短时域 BPTT，把训练人类动作跟踪策略的成本从「上千 GPU 小时」压到「单卡几小时」。它的卖点就是**省算力**，所以我们选择在**最弱的合理硬件**上验证这条主张——如果 8 GB 笔记本也能跑出接近的结果，说明「算力不再是瓶颈」这个论断是成立的。

约束：

| 约束 | 具体 | 直接影响 |
|---|---|---|
| 显存 8 GB | 桌面本身占约 2.1 GB | 训练峰值被压在 2.6 GB |
| 数据必须放得下显存 | BONES-SEED 全库 fp16 = 6.7 GB | 只能用 LAFAN1（40 条 / 2.45 h / 87 MB）|
| Windows 无 MSVC/triton | `torch.compile` 不可用 | 全程 eager，单步慢 2–3 倍 |
| 单卡 | 无法数据并行 | lr 不做 √N 缩放 |

## 2 与论文的配置差异

论文没有开源代码，本复现基于社区复现项目（见文末致谢）的 Windows / 8 GB 适配版。下表是**实际的配置文件内容**，不是估计值。

| 项 | 论文（Table A.5） | 上游复现（5090） | 本复现（4060 8G） | 倍数变化 |
|---|---|---|---|---|
| 数据集 | BONES-SEED 129,514 条 | LAFAN1 40 条 | LAFAN1 40 条 | — |
| 并行环境 | 4096 / GPU | 4096 | **512** | 1/8 |
| 想象 batch | 4096 rollouts | 4096 | **512** | 1/8 |
| 想象时域 H | 32 | 32 | **16** | 1/2 |
| 世界模型 batch | 10 × 2048 窗口 | 10 × 2048 | **10 × 1024** | 1/2 |
| `torch.compile` | 开 | 开 | **关（eager）** | 慢 2–3× |
| 观测 | 论文口径 | +锚点观测（偏离论文） | +锚点观测 | 同上游 |
| UTD | 0.4 | 0.4 | 0.4 | 不变 |
| γ / TD(λ) | 0.99 / 0.95 | 0.99 / 0.95 | 0.99 / 0.95 | 不变 |
| 训练长度 | 320,000 迭代 | 100,000 | **126,500**（发散前） | — |
| 实测吞吐 | — | ~8.4 it/s | **0.68 it/s**（53.2 h 跑 13.06 万） | 1/12 |

**H=16 的依据**：论文 §4.3 证明，配 critic 时 H=16 等效于无 critic 的 H=32。本复现有 critic，所以减半是论文支持的近似，不是随意砍的。

**锚点观测的代价**：上游复现实测，同一套代码在 LAFAN1 上「论文口径」只有 0.56–0.59，加锚点观测（BeyondMimic 的相对位姿）才到 0.904。也就是说 **0.904 这个数字本身已经偏离论文设定**，与论文的 0.82 不能直接横向比较。本复现沿用锚点观测，因此唯一可比的对手是上游的 0.904。

## 3 结果对比

### 3.1 总表

| 指标 | 论文（LAFAN1，1×H100，1.2 h） | 上游复现（LAFAN1，1×5090，3.3 h） | **本复现（1×4060 8G，53.2 h）** |
|---|---|---|---|
| 归一化回报（宏平均） | 0.82 | **0.904** | **0.854** |
| 归一化回报（帧长加权） | — | — | **0.859** |
| 失败条数 / 40 | — | 3 | **7** |
| 世界模型 8 步预测误差 | 0.007–0.011 | 0.0065–0.0099 | **0.0131** |
| 观测口径 | 论文 | 锚点观测 | 锚点观测 |

### 3.2 怎么读这张表

- **对论文的 0.82：超出 0.034**。但这是不同口径（我们是锚点观测 + 40 条，论文是论文观测），只能作为量级参考。
- **对上游的 0.904：差 0.050（相对 5.5%），失败多 4 条**。这是唯一口径一致的比较，也是本复现真实的差距。
- **世界模型误差略差**（0.0131 vs 0.0065–0.0099），符合预期：世界模型 batch 减半、数据量减到 1/8，拟合精度必然下降。但同一数量级，说明**世界模型没有因为裁剪而失真**，这也是策略能收敛到 0.85 的前提。

### 3.3 训练过程

| 迭代 | 40 条宏平均 | 说明 |
|---|---|---|
| 1,000 | 0.333 | 站起来就倒，平均撑 1–2 秒 |
| 31,500 | 0.701（3 条） | 走、跳能跑完整段，跑还差 |
| 74,000 | 0.850（3 条） | 三条全部跑完 |
| **126,500** | **0.854（40 条）** | **交付模型** |

训练回报曲线（`train/episode_norm_return`，滑动平均）从 0.36 升到 0.77，8 万迭代后趋于平台。注意训练曲线数值低于停训实测值，因为训练回合使用随机重置起点、动作噪声与 10 秒截断，实测是确定性、从首帧起播——两者口径不同。

## 5 工程问题与处置

复现过程本身比跑通更花时间。这里记录四个必须解决的问题，供后来者参考。

### 5.1 CUDA illegal instruction（715）——贯穿全程

**现象**：训练进程平均每 1 小时崩溃一次，报 `torch.AcceleratorError: CUDA error: an illegal instruction was encountered`，栈在 `wm_trainer.update() -> loss.backward()`；随后级联刷 `Warp CUDA error 715 (wp_free_device_async, warp.cu:912)`。累计 54 次。

**关键观察**：Warp 初始化打印 `CUDA Toolkit 13.4, Driver 13.0`——**驱动报告的 CUDA 版本低于 Warp 自带编译工具链**。这是此类 715 的典型诱因，怀疑 PTX 版本不被驱动完全支持。

**处置**（未根治，靠工程手段扛住）：

1. 存档间隔从 2000 降到 **500** 迭代，单次崩溃最多损失 10 分钟（最初一次崩溃发生在第 1500 迭代、首次存档前，导致一个档都没存下来，白跑 39 分钟——这是最大的教训）。
2. 写守护进程，崩溃后自动 `--resume ckpt_latest.pt` 重启。最终 **54 个子进程全部以 rc=1 退出，0 次正常结束**，但训练仍然推进到 12.65 万迭代。
3. 世界模型 batch 2048 → 1024，把崩溃现场（wm backward，全流程最大的单次显存分配）的峰值减半。副作用是速度反而从 0.7 升到 0.8 it/s。

**真正该做的**是把显卡驱动升到支持 CUDA 13.4 的版本，本次未做。

### 5.2 评测进程无法与训练共存

`eval_benchmark.py` 和 `record_rollout.py` 在训练占用 GPU 时会**在第一次 `env.step` 立刻崩溃**（同一 715，崩点固定在 `rewards.py:54`）。15 次「训练中拍快照」全部失败，0 成功；停掉训练后单独跑则 100% 成功。

因此所有有效评测都必须**先停训练**。这也说明 `eval_benchmark.py` 即使单独跑也不稳定（曾单独跑也 rc=1），最终全部改用 `record_rollout.py` 逐条记录步数和回报来算指标——它有相同的信息量（跑完步数 / 总步数 / 回报），但走的是另一条代码路径，稳定得多。

### 5.3 训练在第 126,900 迭代发散

`it 126,850 → 126,900` 之间，世界模型在 50 个迭代内直接变成 NaN（此前 `nse1 0.0075`、`imag_ret 1.338` 恰是全程最佳）。之后 3,700 次迭代（约 1.5 小时）全部作废；13 万起的存档含 20 个 policy NaN 张量、14 个 wm NaN 张量，不可用。

**交付模型回退到 `ckpt_0126500.pt`**。发散原因未定论，怀疑与漫长的进程反复崩溃/恢复、优化器动量在异常批次上累积有关。**长跑必须做 NaN 检测 + 自动回滚**，这次是事后发现的。

### 5.4 Windows 侧的环境坑

| 问题 | 表现 | 处置 |
|---|---|---|
| uv 内置 git 拉 github 断流 | `RPC failed; curl 56 schannel` / `early EOF` | 用系统 git 手动 `fetch --depth 1 <commit>`，`pyproject.toml` 改指本地路径 |
| `tyro` 传 `none` 给 `torch.compile` | 把字符串 `"none"` 当编译模式 | 直接改默认值为 `None` |
| `tyro` 的 `list[str]` 只认最后一个 | `--segments` 只生效最后一项 | 一次给全所有值 |
| 无 ffmpeg | 渲染脚本 `FileNotFoundError` | 复制 `imageio_ffmpeg` 自带二进制到 `.bin/ffmpeg.exe` |
| 进程随 agent 会话被回收 | 长任务无法脱离 | 用宿主托管的常驻后台任务 + 断点续训脚本 |

## 6 结论：达到论文水平了吗

**没有完全达到，但已经很接近，且差距可解释。**

- 对论文 LAFAN1 的 0.82：**超出**（但口径不同，仅供参考）
- 对上游 5090 的 0.904：**差 0.05（5.5%），失败多 4 条**
- 论文明星指标「单卡 3 小时超过集群级 PPO」：**本机做不到**——8 GB 显存下需要 53 小时

差距的归因很清楚，不是方法失效：

1. **每条迭代的样本量只有 1/8**（512 env vs 4096，batch 512 vs 4096）。跑了同样的圈数，每圈的训练量少一个数量级。
2. **H=16 削弱了长时域能力**，直接体现在 fallAndGetUp 一族（需要长时域接触推理）全线低于 0.80。
3. **无 `torch.compile`**，同样迭代数要多花 2–3 倍时间，导致 53 小时内只能跑 12.65 万迭代。

反过来说，这套裁剪在 8 GB 上是**成立的**：世界模型误差仍在 0.0131（论文 0.007–0.011 的同一量级），策略能收敛到 0.854，行走类甚至超过上游均值。这说明论文「用世界模型摊销动作库、让算力不再是瓶颈」的核心论点，在消费级硬件上依然站得住。

## 7 复现步骤

```bash
# 1 环境（Python 3.12 + uv）
git clone <this-repo> && cd supermimic-8g
uv sync --group dev

# 2 数据（ModelScope 宇树官方镜像，国内直连，40 条 / 87 MB）
#    见 docs/UPSTREAM_README.md 的数据章节，或直接用 tools/ 下的说明
.venv/Scripts/python.exe scripts/data/csv_to_npz_batch.py \
    --input-dir data/raw/lafan1_ms/g1 --output-dir data/npz/lafan1 --input-fps 30 --workers 16

# 3 训练（带崩溃自动续训）
.venv/Scripts/python.exe tools/supervise_8g.py --hours 30 --ckpt-interval 500

# 4 评测（必须先停训练！）
.venv/Scripts/python.exe tools/snapshot_8g.py
```

**双处必改**（否则起不来）：
- `src/supermimic/world_model/wm_trainer.py` — `compile` 默认值 `"default"` → `None`
- `src/supermimic/imagination/policy_trainer.py` — 同上

`--env.anchor-obs` 只需开启一次：`loop.py` 会自动同步 `policy.goal_dim`（680 → 689）与 `policy_trainer.anchor_obs`。

## 8 局限与后续

**本次未做**

- 真机部署（论文的核心贡献之一）：ONNX/JIT 导出、`unitree_sdk2` 侧推理、50 Hz 参考帧时钟对齐，两个开源实现都没有覆盖。
- BONES-SEED 大规模库（129,514 条）：fp16 库 6.7 GB，8 GB 显存放不下。
- 速度接口（论文 §4.5 的 RL encoder vs 蒸馏对比）。
- 40 条标准 `eval_benchmark`：因 CUDA 715 未跑通，改用 `record_rollout` 等价口径。

**优先级建议**

1. 升显卡驱动到 CUDA 13.4 对应版本 —— 一次性解决 54 次崩溃 + 评测无法并发两个问题。
2. 提高 `fallAndGetUp` 类采样权重后 finetune，预期宏平均可再涨 0.02–0.03。
3. 若要多天长跑，加 NaN 检测与自动回滚到上一个健康存档。
